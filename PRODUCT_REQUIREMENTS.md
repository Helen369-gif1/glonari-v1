# Glonari Global Scene — Product Requirements Document

Status: DRAFT — planning only, no implementation performed.
Date: 2026-08-17

---

## 1. Product overview

Glonari Global Scene is a single-screen, illustrated "city scene" web experience. A composited skyline (sky + seven buildings + a foreground plaza) forms one visual scene, transferred from Figma into a static HTML/CSS page. The long-term product intent (per this planning request) is to evolve this static composition into an interactive experience: a branded loading sequence, a softly cursor-reactive scene, and select interactive building layers that open panels/modals — while preserving the original Figma composition as the visual foundation.

## 2. Product goals

- Preserve the Figma-derived visual composition exactly (composition, proportions, imagery, typography, hierarchy) while layering in interactivity.
- Introduce a distinct Loading Screen system ahead of the main scene ~~(design TBD)~~.
  > **SUPERSEDED (2026-08-25)** — design decided and implemented as a branded intro overlay. See §8 for the full resolved spec and DEVELOPMENT_PLAN.md Stage 4's IMPLEMENTED note for what shipped.
- Give the main scene a slow, soft, elegant, mouse-reactive global movement (reference: Aircord.co.jp hero, first screen only) — all layers move together as one unit, not classic multi-speed parallax. **SUPERSEDED (2026-08-18):** see §10 — replaced by per-layer depth parallax, requested explicitly by the user.
- Make individual buildings independently interactive (hover/click → future panels/modals) without those local effects fighting the global movement.
- Do all of this in controlled, independently shippable stages — not one large rewrite.

## 4. Existing technical structure

**Stack:** Plain HTML5 + plain CSS3. No preprocessor, no framework, no JS runtime dependency.

**Markup (`index.html`):** One root `<div class="scene" data-name="Glonari-Global-Scene">` containing 9 child `<div class="layer …">` elements in DOM order:
1. `.sky` — background sky image
2. `.building.building-global-connections`
3. `.building.building-glonari-news`
4. `.building.building-pulse`
5. `.building.building-persona`
6. `.building.building-banker`
7. `.building.building-global-dream`
8. `.building.building-glonari-ancillary`
9. `.plaza` — foreground plaza/fountain image (rendered last = visually on top)

Each layer wraps a single `<img>`. Seven of the nine images use a `.fill.cover` class (`position:absolute; inset:0; object-fit:cover`); two (`glonari-ancillary`, `plaza`) use bespoke crop wrapper classes (`.crop-ancillary`, `.crop-plaza`) that oversize and offset the image inside an `overflow:hidden` container instead of using `object-fit`.

**Layout/positioning (`styles.css`):** Every layer is positioned with `position:absolute` and percentage-based `left/top/width/height`, with CSS comments giving the exact originating Figma pixel values (e.g. `/* 2 / 2050 */`), confirming the coordinates were computed directly from a **2050×800 Figma frame**. The root `.scene` uses `aspect-ratio: 2050/800`, `width:100%`, `max-width:2050px`, `overflow:hidden` to scale the whole composition fluidly while locking its aspect ratio. `<body>` is a flex container centering `.scene` horizontally, with a navy `#0b1e3a` background filling any space beyond `max-width`.

**No JS, no animation, no media queries, no z-index** anywhere. Stacking order is entirely DOM-order-dependent. All images carry `pointer-events:none`, so nothing on the page currently responds to mouse or touch input.

## 5. Visual preservation requirements

The following must be preserved unless a future requirement explicitly overrides them:
- Overall composition and layer stacking order (sky → buildings left-to-right → plaza foreground).
- Every layer's relative position, size, and proportion as derived from the 2050×800 Figma frame.
- All existing image assets, at existing resolution/content (no placeholder swaps).
- The fluid, aspect-ratio-locked scaling behavior of `.scene`.
- The two bespoke crop techniques on `glonari-ancillary` and `plaza` — these are deliberate Figma-accurate crops, not bugs, and must not be "simplified" to plain `object-fit:cover` without checking that the visual result still matches Figma.

Resolution per bullet:
> - **Visual design:** full-screen overlay; background is the scene's existing deep navy (`#0b1e3a`, already used by `styles.css`'s `html,body`/`.stage-viewport`); a thin warm-gold (`--gold-bright`, the same accent as the custom cursor/building hover glow/section modal) circular mark centered in the viewport, with "WELCOME TO" above the more prominent "GLONARI" beneath/inside it. > - **Minimum display duration:** ~1.5s, even if the readiness signal below fires sooner.
> - **Exit transition:** a brief enlarge of the gold mark ("the Glonari world gently opening"), then a smooth opacity fade of the whole overlay to transparent, then full removal from the DOM (not left as an invisible blocker). Reduced-motion gets a plain fade with no enlarge/rotate.
> - **"Main scene ready" signal:** the page's own `load` event (or `document.readyState === 'complete'` if already true) — chosen because neither `main.js` exposes a custom readiness event, and this doesn't require inventing one; no per-asset `Promise.all`/`decode()` plumbing was added. > - **Accessibility:** `aria-hidden="true"` on the overlay (transient/decorative, so screen readers proceed straight to the Campus); no `aria-live` announcements; no interactive controls; never steals or traps focus.

Same overlay architecture (shared `intro.css`/`intro.js`, `#intro-overlay`, the same fade-to-transparent-then-remove exit) — see DEVELOPMENT_PLAN.md Stage 4's matching 2026-09-21 note for the full file-level writeup. Updated resolution per bullet, only where it changed:
> - **Visual design:** the real logo (`assets/glonari-logo.png`/`.webp`) replaces the traced circle mark; a headline ("More than a place to live — a smarter path to ownership") and subhead (Glonari's real-estate/member-participation/AI/global-connections/financial-intelligence copy, ending "Gia quietly connects it all.") replace "WELCOME TO"/"GLONARI"; a pill-shaped, gold-outlined, no-fill "explore" button is added — the loading screen is no longer button-less. Same navy/gold palette, unchanged.
> - **Progress strategy:** still decorative/indeterminate, no percentage or progress bar — unchanged.
> - **Minimum display duration → reveal duration:** this concept is replaced, not just retimed. There is no longer a "minimum time before exit is even eligible" — exit isn't tied to a duration at all anymore (see next bullet). What used to be the ~1.5s minimum is now the GSAP-driven reveal choreography's own length (logo → copy → button, ~1.5s to a fully-settled button), which is about how long the visitor waits to see everything, not about when the overlay is allowed to leave.
> - **Exit transition:** unchanged (opacity fade of the whole overlay to transparent, then DOM removal; reduced-motion gets a plain fade). What triggers it changed completely — see next bullet.
> - **"Main scene ready" signal / exit trigger:** the `load`-event readiness check is gone. > - **Failure/fallback behavior:** two independent layers now, replacing the old single 3.5s hard ceiling. > - **Accessibility:** `aria-hidden="true"` is **removed** from the overlay, not carried over — it was correct for a transient/decorative screen with no interactive controls, but the overlay now contains a real focusable "explore" button, and hiding it from assistive tech while leaving it tab-reachable would be invalid. Still no `aria-live` announcements; still never traps focus (one focusable element, no focus loop needed).
> - **Not part of this project's own design decision, but worth recording:** the reveal is now built on GSAP 3.12.7 (`cdn.jsdelivr.net`), the same version already used by `digital-banker/lobby/index.html`, chosen for one GSAP version across the project rather than introducing a second. No mobile-specific fork — same shared markup/CSS/JS as desktop, sized via the same 768px breakpoint the old circle mark already used.

## 10. Global mouse-controlled scene movement requirements

Confirmed direction (from this request):
- Reference: **Aircord.co.jp**, first screen / hero only — motion feel, not literal visual design.
- NOT a multi-speed/multi-depth parallax system. All participating layers move together as a single unit; their relative positions to each other stay fixed during movement.
- Desired feel: smooth, soft, elegant, slow/eased, primarily horizontal with only slight vertical movement, not rigid 1:1 cursor tracking, with a soft curved/arc-like quality to the resulting motion path.
- Must return smoothly to a neutral/default position when the cursor leaves the active area.
- Must avoid exposing empty edges/background beyond the composition during movement (a real architectural constraint — see §22 and the Development Plan Stage 5).
- Must respect `prefers-reduced-motion`.
- Must degrade sensibly on touch/mobile where there is no persistent cursor.

OPEN / TO BE DEFINED (explicitly deferred to Development Plan Stage 6, after reference analysis):
- Exact cursor-to-offset mapping function and easing curve.
- Exact horizontal/vertical amplitude limits (in px or % of scene size).
- Smoothing/interpolation algorithm (e.g. lerp per frame vs spring physics).
- What produces the "curved/arc-like" quality mathematically (e.g. non-linear mapping, slight rotation, combined translate+rotate, or an actual curved path function) — NOT assumed yet.
- Whether movement is scoped to the whole viewport, or only an explicit "scene container" region.
- Any interaction with scroll (this is described as a first-screen/hero-style effect; whether the page scrolls at all beyond this scene is currently UNKNOWN).

> **SUPERSEDED / CORRECTED:** A first implementation of Stages 5–7 (fixed `--world-scale-x:1.12`/`--world-scale-y:1.04` headroom filled with a navy color buffer, `.stage-viewport` capped at `max-width:2050px`/`aspect-ratio:2050/800`, fixed `±4.5vw`/`±1.5vh` amplitude) was rejected: it rendered the desktop scene as a long low strip that did not fill the viewport height. The following are now **confirmed** requirements, replacing the corresponding "open" items above:
> - **Desktop scene fills the full browser viewport** — full width, full height, no empty strip above or below.
> - The 2050×800 Figma frame is the **logical/internal coordinate system** only, not the visible viewport size. Desktop rendering uses an `object-fit: cover`-equivalent fit (`scale = max(viewportWidth/2050, viewportHeight/800)`, plus a small overscan margin for safe vertical travel), computed per viewport and applied to a `.scene-world` layer sized in real pixels.
> - Because the Figma frame's aspect ratio (2.5625) is much wider than any realistic desktop viewport, the wide composition **intentionally** extends beyond the left/right viewport edges once it covers full height — this is correct, not a layout bug, and is the real space mouse movement explores.
> - Safe horizontal/vertical travel is derived from **actual rendered overflow** (`renderWidth/Height` vs viewport size), not from an artificial buffer layer or fixed percentage-of-viewport constants. Empty edges must never become visible, by construction (translate range is bounded by real overflow on all sides).
> - Cursor-to-offset mapping is linear per axis; horizontal amplitude is naturally dominant over vertical because of the composition's own aspect ratio, not because of different easing speeds per axis.
> - Smoothing is a single shared time-independent exponential damping constant (not per-axis differentiated tau).
> - This is not classic parallax: all 9 layers still move together via one shared transform on `.scene-world`.
> - A desktop custom cursor was added as part of this correction (not part of the original request): a small gold dot plus a softly trailing gold ring, `pointer-events:none`, shown only on fine-pointer/hover-capable devices (`(hover:hover) and (pointer:fine)`), fully independent of the scene's own movement transform. No custom cursor on touch/coarse-pointer devices.
> Implementation status: technically complete per this correction, verified mathematically and via automated headless-browser rendering — pending manual visual approval.

> **SUPERSEDED (2026-08-18)** — the "NOT a multi-speed/multi-depth parallax system... all layers move together as a single unit" requirement (both the bullet at the top of this section and the "not classic parallax" line in the correction block just above) is replaced by an explicitly user-requested **per-layer depth parallax**: sky, each of the 7 buildings, and plaza now each move at their own rate off the same shared eased pointer offset. This was a deliberate, explicit reversal requested in chat, not a bug or scope creep. Buildings' depths are derived mathematically from their real position in the 2050×800 frame (not hand-picked), so every building remains fully revealable at its own relevant pointer extreme; sky/plaza keep fixed reference depths (0.2 / 1.1). See DEVELOPMENT_PLAN.md Stage 7's matching supersession note for the full accepted architecture and verification method.

>
> **Approach chosen: a synchronous JS viewport-width check, not a CSS media query.** A `<script>` inline in `index.html`'s `<head>` — placed right after `<meta name="viewport">` (so the check already sees the real, post-viewport-meta device width, not a browser's pre-viewport-meta desktop-width default) and before every `<link rel="stylesheet">`/asset on the page — evaluates `window.matchMedia('(max-width: 767px)').matches` and, if true, calls `window.location.replace('mobile/index.html')`.
>
> **Why JS instead of pure CSS**, given the task named both as options: CSS media queries can show/hide/restyle content *within a single document*, but `index.html` and `mobile/index.html` are two separate documents/entry points with almost entirely different markup (parallax `.scene`/`.layer` tree vs. a flat image + `.tap-zone` overlay) — no CSS rule can navigate the browser to a different URL. Only script-driven navigation can actually route between them, which is what "leads the user to the desktop or mobile version" requires. The condition itself still reuses a CSS media-query expression (`matchMedia`), just evaluated in JS so its result can drive a `location` change rather than a style change.
>
> **Why 767px:** matches this project's own already-established mobile breakpoint (see the reverted `max-width: 767px` interim-fix attempts earlier in this section's history) — reusing the existing convention rather than inventing a second breakpoint number for the same concept.
>
> **Why in `<head>`, before stylesheets/assets, and not e.g. after full page load:** the point of the gate is that a phone-sized viewport should never load the desktop scene's assets at all (parallax layer images, `main.js`, `section-modal.js`) just to immediately discard them — running the check as the very first script, before the browser has requested anything else on the page, keeps that request cost off phones entirely (modulo the one already-necessary request for `index.html` itself).
>
> **Why `location.replace()` and not `location.href`:** `.replace()` swaps the current history entry instead of pushing a new one, so a mobile visitor's back button doesn't land back on `index.html` only to be redirected again — it goes to whatever they visited before this site.
>
> **Deliberately viewport-width-based, not touch/pointer-based:** the gate checks screen size, not input capability. A touch-enabled laptop with a wide screen is intentionally kept on the desktop scene (which already has its own independent fine-pointer/hover detection for the custom cursor, `finePointerQuery` in `main.js` — unrelated and unaffected by this gate) rather than being routed to the fixed-440px-wide mobile scene it would render badly on. This matches Stage 14's own decision scope: that decision was about narrow/portrait viewports having no mouse to pan with, not about touch capability in general.
>
> **Known, deliberate limitations (not silently incomplete):**
> - **One-directional only.** The gate lives in root `index.html` and sends narrow viewports to `mobile/index.html`; `mobile/index.html` has no matching reverse check, so a wide-viewport visitor who deep-links or resizes into `mobile/index.html` directly stays there. Not addressed here — flagged as an open item, not assumed away.
> - **Checked once on load, not on resize.** Resizing an already-loaded desktop window narrower does not trigger a live redirect — re-routing continuously while the user is actively resizing their own window would fight them, and desktop's existing `layout()`/`resize` handling in `main.js` already re-fits the scene to whatever width it's given. The gate decides which *scene* loads, once, not which layout renders at every width.
> - **No-JS fallback is the desktop scene.** With JavaScript disabled, the gate never runs and a phone gets the desktop parallax scene (functional per Stage 7–10, just not the intended mobile experience) rather than a broken page — a silent full-capability fallback, not a hard failure, but still worth naming as a real (if edge-case) gap.
>
